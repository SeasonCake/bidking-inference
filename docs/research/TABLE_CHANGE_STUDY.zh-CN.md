# 六十多个表：先证明变了什么，再解释影响

**历史背景：** 2026-09-03的两遍静态集合比较记录中，旧集合61名、新集合62名，
新增1（GuildLevel）、changed 24、unchanged 37、removed 0；两遍新集合名称一致。
这是一段集合与字节比较的历史汇总，不是62张表的全部列语义都已理解，也不是本次重新提取的结果。

本批不附当前62份原表或游戏bundle。可运行部分是
[research.tables](../../research/tables)：共同TSV解析层、显式schema、有界目录差分，
配五名人工前后集合。人工demo数字与历史61→62数字不能互换。

## 四层证据，不合并成一个绿灯

| 层 | 需要记录 | 可以推翻结论的例子 |
| --- | --- | --- |
| 文件身份 | 输入集合、路径名、原字节长度与hash | 同名不同内容、缺文件、混入另一版本 |
| 文本/结构 | 解码策略、BOM/换行、列数、header、主键 | 解码成功但行宽不同；重复ID；新增未知列 |
| 业务语义 | 每列类型/单位/默认/别名、关键字段的消费者 | 列数没变但单位从件数换成格数 |
| 实際行为 | reader→状态→计算→输出，正反例 | parser能读但新列让报价取了旧索引 |

```text
61 old names + 62 new names       (historical summary)
          -> 1 added / 0 removed
          -> 24 byte-changed / 37 byte-unchanged
          -> review the affected consumers
          -> focused runtime cases, not blanket compatibility
```

字节变化不一定是语义变化：BOM或CRLF/LF可以改变hash而不改变解析后的单元格。
反过来，“规范化相同”也只证明该规范化保留的部分相同，不证明编码、
行顺序或应用忽略的字段永远没有意义。

## 人工工具该怎样读

CLI要求显式输入目录和schema，不从本机自动找游戏。它限制文件数、单文件与总字节，
拒绝链接/重解析点，不递归扩大到相邻目录。未知表/非表文本不会被算作schema验证通过。
同一个解析函数既服务解码演示，又服务结构差分，避免两个reader得出不同含义。

演示包含新增/删除、BOM-only变化、新增列、重复ID与原样表；
更多错误形状由单元测试覆盖。命令及实际输出合同见
[Python工具页](PYTHON_TOOLS.zh-CN.md)。差分报告不是自动迁移指令：
遇到结构报警应先定位受影响consumer，不按新增列数量猜兼容程度。

## 一个可贡献的小实验

选三张自造表：item、map、rule，各给before/after。
先画出 `字段 -> 转换 -> 使用者 -> 输出` 的精确映射，再改一项单位或默认值，
让“字节/结构正常而语义错误”的反例被consumer测试抓住。
提交输入、schema、命令和预期差异即可；不需要分享整个游戏数据集。
